# Per-process CUDA memory receipts

`cuda.usage(reset_peak)` counts live `DeviceBuffer` and `HostBuffer` bytes and their respective high-water marks (`peak`, `host_peak`). Both peaks reset atomically to their live counts when requested. A freed transient still contributes to its interval peak. `cuda.memory.takeUsage()` returns the completed interval and resets both peaks under the same lock, so a diagnostic can retain the peak that a reset would otherwise discard. Counts track requested live buffer lengths; borrowed carveouts are excluded. Arena backing reservations and slack are not measured by these logical buffer counts. They exclude CUDA context, NCCL, driver, library and other allocations outside these wrappers. They are neither global GPU usage nor total physical footprint.

`cuda.memory_receipt.emit(rank, phase, reset)` emits a `TF_MEMORY` JSON line only with `TF_CUDA_MEMORY_RECEIPTS=1`. A family can call it at load_begin (reset=true), load_end, cleanup_begin and cleanup_end. Use `takeUsage()` and `emitUsage(rank, .reset, true, completed_interval)` when another API resets peaks; that reset receipt retains the completed interval, while a load_begin receipt describes the newly reset baseline. Receipts name rank, PID, local monotonic time, reset flag and accounting scope. Calls take no CUDA measurements and perform no device synchronization. The caller must establish the load/cleanup boundary. A failed clock is null and cannot qualify an interval. Without family calls, allocator receipts remain unmeasured.

For each rank and context, run a fresh process under the machine owner's existing lock/admission adapter. The following is an input recipe for a future authorized window, not an instruction to access or stop a shared host:

```sh
OWNER_ADAPTER --exec python3 tools/memory_receipts.py \
  --rank 1 --context-tokens 2048 --output rank1-context2048 -- NATIVE_COMMAND ARGS
```

The context value is an operator label, not proof of native context configuration; retain actual launch settings and request token arrays. Use rank 0 and rank 1 independently on their respective hosts with identical context, checkpoint and runtime settings. The adapter must hold the existing owner lock for the wrapper and child's entire lifetime. The wrapper has no admission, remote access or service control. It launches exactly the supplied command; that command must exec the native rank directly, not leave a launcher parent. A mismatched native PID is unmeasured. Preserve existing signal/cleanup ownership when integrating a launcher; do not reuse a native-PID cleanup receipt for this wrapper PID.

The wrapper starts observation before the child runs, samples `/proc/PID/status` and optional `smaps_rollup`, waits for that owned child with `wait4`, and records exit status and boundaries. Linux `ru_maxrss` is an OS lifetime peak resident set, including peaks between samples; it cannot reset. Each fresh process therefore defines one context interval, including fork/exec and startup overhead, not only model allocations. Sampled RSS/PSS/Locked values retain their own timestamps and do not establish between-sample PSS/locked peaks. Permission failure or unsupported readings remain absent/unmeasured, never zero.

A complete native lifecycle has one initial reset and all four ordered load/cleanup phases. Later resets remain visible as separate intervals; never compare an interval peak to a lifetime peak without naming the boundary. A failed child or missing cleanup is unmeasured. After cleanup, nonzero tracked bytes are reported as residual bytes, not silently declared a leak or zeroed. Borrowed resources or process-global owners need separate explanation.

Linux total unified-memory physical-footprint peaks are explicitly **unsupported** here. RSS/PSS plus owned CUDA buffers cannot safely be added: pages may overlap and driver allocations may be absent. The required full physical-footprint qualification remains held until a platform-qualified method with the same rank/load/context/cleanup boundaries is supplied. No host fixture, zero counter, successful tool invocation or JSON manifest qualifies GB10/model memory.

Run host checks with `PYTHONDONTWRITEBYTECODE=1 python3 -m unittest discover -s tools -p test_memory_receipts.py -v` and `zig build test-cuda-host`, plus the repository's full project checks. Tests exercise pinned transient/reset accounting, concurrent reset exclusion, both-rank receipt parsing, missing/invalid evidence and real CPU child RSS/exit collection. They do not allocate CUDA memory or qualify a GPU.
