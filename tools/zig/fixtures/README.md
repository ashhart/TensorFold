# Reference outputs for the Nemotron Intel GPU checks

`ref_nemotron.json` and `ref_nemotron_wide.json` are measurements of the TensorFold 0.6.4 CUDA engine (an NVIDIA GB10 in a
container image with torch 2.13 and CUDA 13), run on the checkpoint `TensorFold/NVIDIA-Nemotron-3.5-Lightning-30B-A3B-MLX-4bit`
(revision `d9d758fb83953437f7263256b0d96157e2a348b8`): serial greedy decoding (temperature 0), the MTP head not loaded, no chat
template, raw token ids without a BOS token. Per generated token the files hold the token id, the five (wide: more) largest
log-probabilities and the log-probability of the chosen token, as `log_softmax` of the float32 conversion of the bf16 logits.

| File | Prompts | Steps | Size |
| --- | --- | --- | --- |
| `ref_nemotron.json` | 4 | 48 each | 38 KB |
| `ref_nemotron_wide.json` | 15, from 4 to 1,850 prompt tokens | 96 each (1,440 positions) | 299 KB |

Prompt sources: the four short prompts of the first file and the first four of the second ("The capital of France is", a Python
function header, "Once upon a time", a 305-token passage) were written for this test. The other eleven prompts of the second file are
slices of the first column of the wikitext-2 raw training text at the character offsets in their `text` field ("wikitext@OFFSET len
N"), stored as token ids of the Nemotron tokenizer. WikiText-2 is by Stephen Merity et al. ("Pointer Sentinel Mixture Models"),
distributed under the Creative Commons Attribution-ShareAlike 3.0 license (https://creativecommons.org/licenses/by-sa/3.0/); the
token ids in `ref_nemotron_wide.json` derive from it and carry the same license. The generated token ids and log-probabilities are
measurements of the engine named above on those prompts.

Used by `tools/zig/xpu_compare_ref.py` (forced-token and greedy agreement) and `tools/zig/xpu_compare_wide.py` (1,440 forced positions).
Per-operation fixtures are not shipped because they contain slices of the checkpoint's weights; `tools/zig/xpu_fixtures_*.py`
regenerate them from a local checkpoint.

## `e4b_layer_input_mlx.json`

SHA-256 prints of MLX's output at every step of the Gemma 4 E-series per-layer inputs and block at the E4B's shapes (2560 hidden,
256 per-layer inputs, 3 layers, 4 tokens, 13 steps each), plus nn.gelu_approx over the finite bf16 patterns, with the MLX 0.32.4 and
mlx-lm 0.32.2 versions, the device (Apple M4 Max GPU), the streams and the operations; one row at a time (M = 1). About 14 KB.
`tools/zig/gemma4_e4b_layer_input_oracle.py` writes it. The inputs and weights are seeded (splitmix64) and regenerated by the test, so
nothing of a checkpoint is stored. The "SHA-256 prints" test in `zig/src/families/gemma4/layer_input_mlx_test.zig` chains the host's own steps,
hashes each one's bf16 bytes and names the first token, layer and step that differ; it skips when the file is absent.
`--full` also writes `e4b_layer_input_mlx.bin` (432 KB, MLX's outputs themselves, git-ignored); with it present a second test feeds
each step MLX's previous output and compares the values. The prints are deterministic on a given MLX and chip; other versions or chips
may differ in the last bit of a sum (the single-row matmul and rms_norm kernels are chosen by shape and by GPU generation).
An Apple M5 Ultra with the same versions gives the same prints as the M4 Max.

## Synthetic repetition-penalty logits

`zig/tests/cuda/repetition_hf_fixture.h` contains ten model-free cases written for the repetition processor tests.
Every input is an explicit IEEE float32 pattern and every history is a small list of synthetic token IDs.
Finite logits are exactly representable in BF16. The reference keeps the processed logits in float32.
The cases cover signs, signed zero, duplicate IDs, identity and below-one factors, empty history, infinities,
NaNs, greedy changes and a value whose winner would change if processed logits were rounded back to BF16.
They contain no checkpoint weights, tokenizer output or conversation data.

`tools/zig/repetition_hf_fixture.py` calls the actual
`transformers.generation.logits_process.RepetitionPenaltyLogitsProcessor` from Transformers **5.20.1** on CPU.
The installed package is an optional developer reference; native inference and native tests do not import it.
Use an isolated environment with a CPU-capable PyTorch installation and `transformers==5.20.1`:

```sh
CUDA_VISIBLE_DEVICES= HF_HUB_OFFLINE=1 TRANSFORMERS_OFFLINE=1 \
  python3 tools/zig/repetition_hf_fixture.py --check zig/tests/cuda/repetition_hf_fixture.h
CUDA_VISIBLE_DEVICES= HF_HUB_OFFLINE=1 TRANSFORMERS_OFFLINE=1 \
  python3 tools/zig/repetition_hf_fixture.py --out zig/tests/cuda/repetition_hf_fixture.h
```

The first command reads and checks the header. The second explicitly regenerates it.
Both print the package versions, processor source hash, header hash, device and dtype as JSON.
The script refuses a different Transformers version.
The original processor is available in the
[Transformers 5.20.1 source](https://github.com/huggingface/transformers/blob/v5.20.1/src/transformers/generation/logits_process.py).

CPU regeneration with Transformers 5.20.1 and PyTorch 2.14.1 reproduced all ten cases byte for byte:
header SHA256 `9388ddb013232071f6290e43a2d91fa1772f539cf7c0d5830e63115f7c5a9dd3`,
processor-class source SHA256 `bada3b1186344c29c3fc79161e865a6d649d1bbcf386d60fb74fb8d471133c1d`.
NaN payload bits can vary through BF16 conversion; the native test checks their NaN class.
The HF processor supplies transformed logits. Greedy selection is checked separately by the native test;
the `0xffffffff` greedy sentinel skips selection for the NaN fixture.
