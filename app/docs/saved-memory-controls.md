# Saved memory in a chat

Open the composer’s More options menu, then Memory. Use saved memory and Propose new memories are independent choices. Save choices applies them to the next turn after encrypted storage accepts the change; a failed save keeps the draft and the previous effective choices. Stop the active turn before changing them. Damaged choices are shown as unknown and require an explicit saved replacement; an invalid revision directs you to a new chat without discarding the old history. If another window or a new turn changes the revision, reopen the menu to review the current choices.

Use saved memory controls TensorFold’s recall of previous chats, saved project facts, freeform project memory and learned room memory, prior room conversations and shared scratch memory. It also gates direct session tools and app-owned child tools. Explicit workspace files, project instructions, configured persona/profile, live connectors, operational room task/status notices and task records keep their existing permissions. Standard chat does not automatically inject project memory; supported retrieval tools may use it when recall is enabled.

Propose new memories controls compaction proposals, successful-run memory proposals, optional automatic skill review and model-origin skill/command suggestions. Enabled contributions are pending proposals with their source conversation and turn where available, requiring human review. Direct user-authored text is considered conservatively: unclassified older text, connector input, quoted text and messages with attachments are excluded from automatic preference harvesting. This can miss a useful preference; deliberate project-memory edits and approvals remain available separately.

Ordinary chat history remains encrypted and saved with either or both controls off. Already-seen conversation context remains visible to the model. These choices do not erase history, remove facts from existing context, undo Living Weights training, or change providers’ and tools’ own retention. Start a new chat for fresh context. Explicit Living Weights Teach remains a separate action; these controls do not trigger training.

Incognito always disables contributions and keeps its existing stricter persistence boundaries. Changing its memory choices does not read or rewrite unrelated protected chat storage. CLI engines and older remote hosts do not advertise enforcement and cannot accept a restricted policy. Existing unrestricted CLI conversations retain their prior behavior; the menu explains that these controls are unavailable on those routes. A restricted chat cannot silently switch or hand off to an unsupported engine.

The host owns the policy, revision and immutable run capture. Generic renderer patches and run payloads cannot override it. The durable transaction publishes live changes only after atomic encrypted replacement, and a per-thread admission lease prevents a run from starting during that save. Forks and supported handoffs copy the choices. App-owned thread children and linked mission passes inherit the captured restrictions; late proposal callbacks also verify the owning chat revision and cancellation state.

Bot and phone-local conversations cannot launch child agents or linked missions; those secondary runtimes do not yet enforce their captured bot permissions and local-processing boundary. Ordinary tasks retain supported child and mission workflows with their saved-memory choices.

Acceptance tests exercise all four combinations through the actual API-model loop and host runtime with deterministic synthetic responses, encrypted storage before the first request, actual compaction, proposal review, current-history preservation, direct retrieval and suggestion callbacks, child inheritance, fork, stale revisions/reviews, active admission, durable failure, quarantine and Incognito. Browser QA uses the actual overflow/settings components in an account-free localhost fixture at desktop and narrow sizes, including pending, failure, retry, active, private, unsupported and stale states. Native application integration and real-model acceptance remain separate release checks.
